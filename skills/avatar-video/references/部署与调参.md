# avatar-video 部署与调参

ComfyUI + InfiniteTalk 14B 在 8GB 显存 / 32GB 内存机器上的完整踩坑记录与调参手册。

## 硬件前提

| 项 | 值 | 影响 |
|----|----|------|
| GPU | RTX 5060 8GB | 必须 block swap，把 38/40 个 block 放在内存 |
| 内存 | 32GB | **加载模型瞬间降到 0.1GB**，任何后台程序都会导致崩溃 |
| 磁盘 | 1TB NVMe | 模型 16.2GB，Whisper medium 1.5GB |

## 一、ComfyUI 启动参数（关键）

必须用这两个参数，缺一不可：

```powershell
D:\Program\ComfyUI\.venv\Scripts\python.exe main.py --disable-async-offload --disable-cuda-malloc
```

### 为什么 `--disable-async-offload`

ComfyUI 默认在 NVIDIA 卡上启用 2 流异步权重卸载（`Using async weight offloading with 2 streams`）。它和 InfiniteTalk 自己的 block swap 抢占同一批显存，表现为：

```
[CUDA driver error: device not ready]
Failed to create GPU mapping
```

**必崩点**：第 3~5 段 clip（开跑 30 分钟左右）。关掉后 14 段全程无崩溃。

### 为什么 `--disable-cuda-malloc`

ComfyUI 默认把 PyTorch 分配器设成 `backend:cudaMallocAsync`（见 `D:\Program\ComfyUI\cuda_malloc.py` L105-112）。如果同时设了 `PYTORCH_CUDA_ALLOC_CONF`，它会**追加** `,backend:cudaMallocAsync`：

```python
env_var = os.environ.get('PYTORCH_CUDA_ALLOC_CONF', None)
if env_var is None:
    env_var = "backend:cudaMallocAsync"
else:
    env_var += ",backend:cudaMallocAsync"   # 冲突！
```

实测 `expandable_segments:True` 虽然能解决显存碎片，但会在 Windows WDDM 上触发映射失败。**结论：不用任何自定义 alloc conf，让它走默认分配器**，靠降低分辨率和定期 `empty_cache` 解决碎片。

## 二、内存管理

### 跑之前必须清后台

加载 14B 模型时内存峰值到 34.2GB（物理 32GB + 页面文件），剩余可用会掉到 **0.1GB**。

实测吃内存大户：

| 程序 | 占用 | 后果 |
|------|------|------|
| Edge + EdgeWebView | 约 2GB | 加载中途 access violation |
| 迅雷（11 进程） | 约 0.8GB | 同上 |
| WorkBuddy | 约 0.8GB | 同上 |
| 微信 | 约 0.17GB | 累积效应 |

**建议**：跑之前关掉这些，`--check` 会显示当前可用内存，低于 15GB 就不该启动。

### 加载期 OOM 的根因与修法

模型加载时 `sd`（safetensors mmap，16.4GB）和转换后的参数（committed，约 16GB）同时存在。已在
`custom_nodes/InfiniteTalk/nodes_model_loading.py` 加了边载边释放：

```python
free_sd_during_load = "scaled" not in quantization
...
if free_sd_during_load:
    sd[name] = None
```

## 三、分辨率与速度

序列长度 = `(宽/16) × (高/16) × 21`，宽高必须是 **16 的倍数**（VAE 8× 下采样 × patch 2）。

### 实测（RTX 5060）

| 分辨率 | seq_len | 每段（10秒） | 14 段总计 |
|--------|---------|-------------|----------|
| 832×480 | 32760 | 20+ 分钟 | 不可行 |
| 640×384 | 20160 | 3.5 分钟 | 约 50 分钟 |
| 416×608 | 20748 | 3.5 分钟 | 约 50 分钟 |

**480×480 是分水岭**：降到这个量级后显存峰值降到 2.6GB，才有足够余量做 block swap 而不崩。

`--area` 像素预算控制：

| area | 对应分辨率（376×546 源图） | 每段 | 画质 |
|------|--------------------------|------|------|
| 180000 | 352×512 | 约 2.5 分钟 | 偏软 |
| 256000 | 416×608 | 约 3.5 分钟 | 平衡（默认） |
| 400000 | 528×768 | 约 5 分钟 | 清晰 |

## 四、图片适配

InfiniteTalk 默认工作流用 `crop` 缩放，竖图（如 376×546）裁成 640×384 会**只保留中间一条横带**，人物被切掉。

`generate_video.py` 的处理：

1. 读图片真实尺寸
2. 按比例算 `/16` 对齐的分辨率（横图、竖图、方图通用，误差 <1.5%）
3. 把 `ImageResizeKJv2` 的 `keep_proportion` 从 `crop` 改成 `pillarbox_blur`（等比缩放 + 模糊背景填充）

**不要用 `crop`**，除非确定素材已经是目标比例。

## 五、Whisper 模型存放

### 位置约定

Whisper 权重放在 `models/avatar-video/whisper/<model>/`，与其他 skill 一致：

```
models/
├── avatar-video/whisper/{tiny,base,small,medium}/
├── lip-sync/{musetalkV15,sd-vae,whisper,dwpose,face-parse-bisent}/
└── tts/Qwen3-TTS-12Hz-0.6B-Base/
```

**不用 huggingface_hub 的缓存**（`~/.cache/huggingface`）有两个原因：

1. 落在 C 盘，白占系统盘空间
2. Windows 不支持 symlink，hub 会把每个文件在 `blobs/` 和 `snapshots/` 各存一份，**占用翻倍**（实测 small 是 925MB 而非 461MB）

可用环境变量覆盖：`AVATAR_VIDEO_WHISPER_DIR`

### 下载

`whisper_srt.py --download <model>` 直接写项目目录。

HF 镜像的坑：设了 `HF_ENDPOINT=https://hf-mirror.com` 后，**大文件会被重定向到官方 xet 存储**（`cas-bridge.xethub.hf.co`），国内直连超时，只下到 2.5MB 就卡住。脚本改用 `resolve` 端点 + `curl` UA 头直拉，绕开 huggingface_hub 的下载逻辑。

所需 4 个文件，缺 `vocabulary.txt` 会报 `Cannot load the vocabulary`：

```
config.json  tokenizer.json  vocabulary.txt  model.bin
```

### 加载方式

脚本传**目录路径**给 `WhisperModel()` 而不是模型名。传名字会让 faster-whisper 去问 huggingface_hub 要 revision，离线报错、在线又会被 xet 卡住。

### 模型选择与速度

实测耗时（31.7 秒音频，CPU int8，模型已在本地）：

| 模型 | 大小 | 耗时 | 中文准确率 |
|------|------|------|-----------|
| tiny | 74MB | 1 秒 | 差（"靠乎"、"专输"） |
| base | 141MB | 2.9 秒 | 一般 |
| small | 464MB | 7.0 秒 | 可用 |
| **medium** | **1.5GB** | **18.3 秒** | **好** |
| large-v3 | 3.1GB | 约 40 秒 | 最好 |

**默认 medium 是合理的**：字幕转写只占视频生成时间的 0.7%（18 秒 vs 42 分钟），换准确率非常划算。

实测 medium 相对 small 修正的错误：「资**询**」（small 听成"资寻"）、「全流**程**」（small 听成"全流成"）。

> 注：`.venv` 下首次加载模型有额外的一次性磁盘读入开销，之后走系统页缓存。

## 六、字幕样式

`burn_subtitle.py` 提供两套，参数值见脚本内 `STYLES`：

| 样式 | 效果 | 适用 |
|------|------|------|
| `corporate` | 微软雅黑细体白字 + 半透明深色底条，距底部 60px | 正式场合、公司介绍 |
| `bottom` | 白字 + 2px 黑描边 + 阴影，距底部 40px | 通用、平台视频 |

ASS 颜色是 `&HAABBGGRR` 格式（注意是 BGRA 不是 RGBA）。

### 中文路径问题

libass 滤镜在 Windows 上有两个坑：

1. **读不了非 ASCII 路径** → SRT 先复制到临时目录
2. **盘符冒号被当成选项分隔符** → `subtitles=/C:/path` 会报 `Unable to parse option value`

脚本的做法：把 SRT 复制到临时目录，ffmpeg 以该目录为 `cwd`，滤镜里用纯相对路径 `filename=sub.srt`，彻底绕开两个问题。

## 七、其他已修的问题

| 问题 | 表现 | 修法 |
|------|------|------|
| T5 编码显存溢出 | `WanVideoTextEncode` 把 6.7GB T5 拷回内存时 OOM | 改为释放引用而非 `.to(cpu)`（`nodes.py`） |
| 释放污染缓存 | 第二次运行 `'NoneType' object has no attribute 'model'` | T5 loader 加 `IS_CHANGED` 强制重载（`nodes_model_loading.py`） |
| 激活显存泄漏 | 每次 forward 累积约 3GB | block forward 里 `del q, k, v, input_x, y`（`wanvideo/modules/model.py`） |
| 显存碎片 | `allocated 6.63GB` 但 `Free 0 bytes` | 每 4 个 block `empty_cache()` |
| transformers 5 兼容 | wav2vec2 `_encoder_forward` 报错 | `multitalk/wav2vec2.py` 加 hidden_states 兼容 |

## 九、耗时参考

| 音频长度 | 分辨率 | 总耗时 |
|----------|--------|--------|
| 9.5 秒 | 416×608 | 16 分钟 |
| 31.7 秒 | 416×608 | 42 分钟 |
| 2.5 分钟 | 416×608 | 约 55 分钟 |
| 2.5 分钟 | 640×384 | 约 50 分钟 |
