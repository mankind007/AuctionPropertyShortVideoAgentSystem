# MuseTalk V1.5 口型对齐 — 部署方法记录

记录「静态人物图 + 音频 → 讲话视频」链路的完整搭建方法，含本机网络受限环境下的踩坑处理。  
人工独立运行入口：`skills/lip-sync/scripts/lipsync.py`（技能规范见 `skills/lip-sync/SKILL.md`）。

## 1. 目标与原理

输入一张人物图和一段音频，用 MuseTalk V1.5 生成口型同步的视频。

核心链路（官方 `scripts/inference.py` 逻辑）：

```
图片 ─┬─ S3FD 人脸检测 ────────> 人脸 bbox
      └─ DWPose(RTMPose-l) 68 点 ─> 计算 crop 上边界
                    │
音频 ── Whisper(tiny) encoder ──> 每帧 audio embedding
                    │
        VAE(ft-mse) 编码 bbox crop ──> 8 通道 latent
                    │
        MuseTalk UNet(audio cross-attn) ──> 预测 latent
                    │
        VAE 解码 ──> 256x256 口型帧 ──> 放回原图 + FaceParsing 融合
                    │
              ffmpeg 合成 mp4 + 音轨
```

- `skills/lip-sync/vendor/MuseTalk/musetalk/utils/face_detection/detection/sfd/s3fd.pth` — 人脸检测权重
- `skills/lip-sync/vendor/MuseTalk/musetalk/utils/dwpose/*.py` — DWPose 配置（代码仓自带）

### 关键：junction

官方代码大量使用相对路径 `./models/...`、`./musetalk/...`，且依赖 **cwd = MuseTalk 仓根**。
权重放在 `models/lip-sync/`，因此用目录联接把 `MuseTalk/models` 指向 `models/lip-sync`：

```powershell
cmd /c mklink /J "<repo>\skills\lip-sync\vendor\MuseTalk\models" "<repo>\models\lip-sync"
```

这样 `cwd=MuseTalk` 时，`./models/musetalkV15`、`./models/sd-vae`、`./models/dwpose`、
`./models/face-parse-bisent`、`./models/whisper` 全部一次解析到位。已由脚本自动创建，幂等。

### 4.3 mmdet / mmpose

MuseTalk 的 DWPose 配置里 backbone 是 `CSPNeXt`，带 `_scope_='mmdet'`，**必须装 mmdet**；
mmpose 负责 `init_model` + `inference_topdown`。

```powershell
uv pip install -i https://pypi.tuna.tsinghua.edu.cn/simple ^
  mmengine "mmdet==3.3.0" "mmpose==1.3.2" --no-build-isolation
```

版本兼容矩阵（重要）：

| 包 | 版本 | 要求 mmcv |
|---|---|---|
| mmpose 1.1.0 / mmdet 3.1.0 | 旧 | `< 2.1.0` ❌ 与 2.2.0 冲突 |
| **mmpose 1.3.2** | 用此 | `2.0.0rc4 ~ 3.0.0` ✅ |
| **mmdet 3.3.0** | 用此 | `>=2.0.0rc4, <2.2.0` ❌ 差一位 |

`mmdet 3.3.0` 的版本守卫是 `< 2.2.0`，mmcv 正好 2.2.0 被拒。
因为 mmcv 2.2.0 对 2.1.0 是向后兼容的，脚本在 **import mmdet 之前** 加 shim 即可绕过（见 §7.1）。

> 注意 `--no-build-isolation` 不可省：省掉它 uv 会在全新隔离环境里重编 `chumpy`，
> 而该临时环境没有 pip，会报错。加上后 uv 用已装好的构建依赖，编译成功。

### 6.1 效果调参（觉得"假"时先动这几个）

| 参数 | 默认 | 作用 | 调优方向 |
|---|---|---|---|
| `--upper-boundary-ratio` | **0.58** | 融合区上边界占 crop 高度的比例 | **唯一真正有效的大旋钮**，见下 |
| `--extra-margin` | 10 | 人脸框下边界外扩像素 | 调**小**会让嘴部变糊、更偏离原图，别动 |
| `--parsing-mode` | jaw | 融合 mask 构建方式 | 实测 `raw`/`jaw`/`neck` 差异在噪声内，**无效** |
| `--left/right-cheek-width` | 90 | 腮部是否参与融合 | 实测 90 vs 140 差异在噪声内，**无效** |
| `--bbox-shift` | 0 | 人脸框上边界平移（官方提示范围见运行日志） | 微调 crop 高度 |
| `--fps` | 25 | 帧率 | 与音频时序绑定，非必要不改 |

**`--upper-boundary-ratio` 的取舍**（在 `man1.jpg` 上实测，见 §11）：

| 取值 | 口型运动幅度 | 保留原图表情 | 说明 |
|---|---|---|---|
| 0.5 | **4.2（最大）** | 差 | 官方默认。原图的露齿笑被整块替换成生成的抿嘴 |
| **0.58** | 4.0（95%） | 好 | **当前默认，平衡点** |
| 0.62 | 3.2（−25%） | 最好 | 融合区压到嘴上，看到的多是原图的嘴 → 静止帧像、但口型跟不上音频 |

> 换图后建议按同样方法快速标定：固定音频，分别用 `0.5 / 0.58 / 0.62` 各出一版，
> 挑「嘴动得明显 + 笑容没丢」的那档。这与素材里人物的表情幅度有关，不是普适常数。

### 6.2 音轨采样率

Whisper 只吃 16kHz 单声道，**但音轨不能用这一份**——早期版本直接 mux 了它，
导致成片音质被压成 `16000 Hz mono`，发闷。现在脚本会产出两份：

- `*_asr.wav` → 喂 Whisper（16k mono）
- `*_mux.wav` → 最终音轨（保留源采样率，实测 48000 Hz stereo）

产物：`assets/lip_sync/<图名>_<音频名>.mp4`（h264 + aac）。
中间帧写在临时目录，结束即删；要留着看就用 `--result-dir` 指定目录。

实测（RTX 3060 Laptop 6GB / 15GB 内存，完整音频不截断）：
`--image assets\man1.jpg --audio assets\me.mp3`
→ 319 帧 @25fps，`assets/lip_sync/man1_me.mp4` 465125 字节，12.76s，860x574，
音轨 48000 Hz stereo。

## 7. 已知问题与处理

### 7.1 mmdet 版本守卫（必须处理）

`mmdet/__init__.py` 里 `mmcv_maximum_version='2.2.0'` 且判断为 `< 2.2.0`，直接 import 报错：

```
AssertionError: MMCV==2.2.0 is used but incompatible. Please install mmcv>=2.0.0rc4, <2.1.0.
```

处理方式：**在 `import mmdet` 之前临时降级版本号**（只影响守卫读到的值，不改动 site-packages，
重装 mmdet 后依然有效）：

```python
import mmcv
mmcv.__version__ = "2.1.0"   # 仅为通过 mmdet<2.2.0 的守卫
import mmdet
```

已被封装进 `skills/lip-sync/scripts/lipsync.py` 的 `load_mmpose_stack()`。

### 7.2 xtcocotools 与 numpy 2

见 §4.4。表现：`ValueError: numpy.dtype size changed ... Expected 96 from C header, got 88`。

### 7.3 官方 inference.py 的图片模式清理 bug

`scripts/inference.py` 中 `save_dir_full` 只在视频分支赋值；图片模式走到
`shutil.rmtree(save_dir_full)` 会 `NameError`，被外层 `except` 吃掉并打印
`Error occurred during processing: ...`。**输出 mp4 此时已经生成**，属可忽略的收尾噪音。
本项目自建推理循环，不复现该问题。

### 7.4 torch 2.6 的 `weights_only` 默认值变更

torch 2.6 起 `torch.load` 的 `weights_only` 默认从 `False` 改为 `True`。
DWPose / BiSeNet 等第三方 checkpoint 内含 numpy 对象，会被拒：

```
_pickle.UnpicklingError: Weights only load failed ...
WeightsUnpickler error: Unsupported global: GLOBAL numpy.core.multiarray._reconstruct ...
```

处理：权重来源可信，用官方开关恢复旧行为（`torch.load` 调用时读取，
**不需要**先于 `import torch`）：

```python
os.environ.setdefault("TORCH_FORCE_NO_WEIGHTS_ONLY_LOAD", "1")
```

已内置在 `skills/lip-sync/scripts/lipsync.py` 模块顶部。

### 7.5 unet.pth 加载：三种 OOM，两种是 native 崩溃

`unet.pth` 849.9M 参数（fp32 = 3.4GB），加载时连踩三个坑，**只有第一个有 Python traceback**：

**坑 1 — GPU OOM（有 traceback，好查）**

官方 `musetalk/models/unet.py` 在 `torch.cuda.is_available()` 时执行
`torch.load(model_path)` **不传 map_location**。该文件由官方脚本在 GPU 上导出，
张量带 cuda 设备标签，于是 torch 按原设备解包，把 3.4GB fp32 直接解到显卡：

```
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 20.00 MiB.
GPU 0 has a total capacity of 6.00 GiB of which 4.14 GiB is free.
Of the allocated memory 872.74 MiB is allocated by PyTorch ...
```

**坑 2 — 物理内存 OOM → `0xC0000005`（无 traceback）**

改成 CPU 加载后，若「先建 `UNet2DConditionModel(**cfg)` 再 `torch.load`」，
峰值变成 **模型 3.4GB + checkpoint 3.4GB = 6.8GB**。

**坑 3 — 字典推导式让新旧两份 dict 并存 → 峰值 5.1GB（无 traceback，且时好时坏）**

即使按坑 2 修好（mmap + meta 初始化），只要 fp16 转换写成推导式：

```python
weights = {k: (v.to(torch.float16) if ... else v.clone())
           for k, v in weights.items()}      # ❌ 新 dict 构建期间旧 dict 仍存活
```

构建过程中 `旧 fp32 (3.4GB) + 新 fp16 (1.7GB) = 5.1GB` 同时在内存里。

本机表现是**间歇性崩溃**——空闲内存 7GB 时能跑过，被浏览器/WorkBuddy 吃到 3.7GB 时
当场死掉。正确写法是**逐条转换并立刻丢弃原引用**：

```python
raw = torch.load(unet_weight, map_location="cpu", mmap=True)
weights = {}
for key in list(raw):
    value = raw.pop(key)                      # 先从源 dict 摘除
    weights[key] = value.to(torch.float16) if value.is_floating_point() else value
    del value                                 # 立刻释放本条 fp32/mmap 引用
del raw
```

峰值降到约 2GB。已封装进 `load_unet_cpu()`。

**为什么必须在 native 崩溃前拦住**

`0xC0000005`（Windows 十进制 `-1073741819`）**没有任何 Python traceback**，
日志会停在最后一行 `torch.load(...)` 或 `weights = ...`，极易误判成 torch 的 bug。

> 排查口诀：`exit=1` = Python 异常；`exit=-1073741819` = native 崩溃 → 优先怀疑内存/越界。

因此脚本在加载前先查可用物理内存，不足直接抛可读错误：

```
[mem] 可用物理内存 2603MB (阈值 2500MB)
```

fp16 阈值 2500MB，fp32 阈值 4500MB。仍需注意这是**加载瞬间**的峰值，
跑之前最好别开着一堆大内存程序。

其余要点：

1. **`from diffusers import UNet2DConditionModel` 必须在 `with torch.device("meta")` 之外**。
   放进去会报 `Failed to import diffusers... Tensor.item() cannot be called on meta tensors`
   —— 是 import 期的张量运算炸了，不是初始化炸了。
2. `load_state_dict(..., assign=True)` 需要 torch ≥ 2.0；本项目 2.6.0 满足。
   实测 `missing=[] unexpected=[]`，无非持久 buffer 残留在 meta 设备。
3. **加载顺序**：先 UNet 再 VAE。`unet.to(device)` 会把 CPU 侧 1.7GB 立刻归还，
   再加载 VAE 才不会两个模型的 CPU 峰值叠加。

> 另注：`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 在本机 torch 2.6 上
> 只会打印 `expandable_segments not supported on this platform`，**没有作用**，不要指望它。

### 7.6 官方 API 签名与直觉不符

`musetalk/utils/preprocessing.py` 里的参数名是 **`upperbondrange`**（官方拼写），
不是 `bbox_shift`（打印文案里才叫 bbox_shift）：

```python
def get_landmark_and_bbox(img_list, upperbondrange=0):   # 不是 bbox_shift=
```

传 `bbox_shift=` 会 `TypeError`。

### 7.7 关键点提完后及时释放 DWPose/S3FD

DWPose(~200MB) + S3FD(~100MB) 在 `import musetalk.utils.preprocessing` 时就上卡，
但整段推理只在开头用一次。6GB 卡上把它们挪回 CPU 能换来约 300MB 余量。

结构是三层，容易放错对象：

```
preprocessing.fa            # FaceAlignment（普通类，不是 nn.Module）
  └─ .face_detector         # SFDDetector（普通类）
       └─ .face_detector    # s3fd（torch.nn.Module，真正要搬的）
```

**`SFDDetector.device` 必须一起改成 `"cpu"`** —— 它的 `detect()` 用 `self.device`
决定输入张量放哪，只搬模块不改 device 会 `net 在 CPU、img 在 cuda` 设备不匹配。

DWPose 那侧简单：`preprocessing.model.to("cpu")` 即可，mmpose 会按模型设备推断推理设备。

已封装进 `release_face_detectors()`。

### 7.8 图片模式帧循环

单张图时 `frame_list` 长度为 1，官方做 `frame_list + frame_list[::-1]` 平滑首尾；
latent 按音频帧序循环复用，即「同一张脸、口型随音频逐帧变化」，这正是静态图驱动说话的标准做法。

### 7.9 图片宽度/高度为奇数：libx264 报 `height not divisible by 2`

`man1.jpg` 是 860×574（宽高均为偶数）没触发；换 `man2.webp`（**374×249，高度是奇数**）
在最后合成阶段报错：

```
[libx264] height not divisible by 2 (374x249)
[vost#0:0/libx264] Error while opening encoder - maybe incorrect parameters
RuntimeError: 帧序列合成失败
```

原因：`libx264 + yuv420p` 要求输出宽高**均为偶数**（色度二次采样每 2×2 像素一组）。
不是 MuseTalk 的问题，是 ffmpeg 编码约束。

处理：合成时强制向下取偶（代价是最多裁掉 1px 边缘，肉眼无感）：

```powershell
ffmpeg ... -i frames/%08d.png `
  -vf "scale=trunc(iw/2)*2:trunc(ih/2)*2" `
  -vcodec libx264 -pix_fmt yuv420p -crf 18 out.mp4
```

已内置在 `skills/lip-sync/scripts/lipsync.py` 的帧序列合成步骤。

验证（2026-09-23）：
- 隔离测试：造 5 张 374×249 帧，不加滤镜精确复现原报错 exit=-1；加滤镜 exit=0，输出 **374×248**
- 端到端：`man2.webp + me.mp3` → `assets/lip_sync/man2_me.mp4`（374×248，319帧/12.76s，48kHz stereo），exit=0
- 回归：`man1.jpg` 成片规格不变（860×574）

## 8. 显存与内存：6GB / 15GB 够不够

**够用，但必须 fp16 + 小 batch，且 UNet 不能按官方方式加载。**

权重 FP16 占用估算：

| 组件 | FP16 约占用 |
|---|---|
| MuseTalk UNet（3.24GB 点对点权重） | ~1.62 GB |
| VAE ft-mse | ~0.16 GB |
| Whisper tiny encoder | ~0.07 GB |
| DWPose RTMPose-l | ~0.20 GB |
| S3FD / BiSeNet | ~0.07 GB |
| 激活 + CUDA context | ~1.0 GB |
| **合计** | **~3.1 GB** |

留有余量，所以：

- **默认就是 fp16**（`--fp16`）；关掉用 `--no-fp16`，此时 UNet 单进程就 ~3.4GB，
  叠加激活和 DWPose 会顶到 6GB 上限，**且 CPU 侧加载阈值提高到 4500MB**
- `batch_size` 默认 8 偏激进，6GB 上建议 **2~4**（脚本默认 2）
- 关键点提完后脚本会自动 `release_face_detectors()` 把 DWPose/S3FD 还给 CPU。
  注意 S3FD 本身**一直跑在 GPU**，只是检测完成后才回收——全片人脸检测只做一次，
  之后的逐帧 UNet 推理才是显存大头

**显存不是唯一的瓶颈**：本机 15GB 物理内存，UNet 加载方式不对会先在 CPU 侧崩（§7.5），
比 GPU OOM 更早发生，而且是**间歇性**的（取决于当时还剩多少空闲内存）。两个都要按 §7.5 处理。

已实测跑通：6GB 卡 + 15GB 内存，完整 12.78 秒音频 / 319 帧，全程无 OOM。

> 30fps 实时推理是 V100(16GB) 的口径；6GB 走离线批量合成没问题，只是慢。

## 11. 效果 A/B 实测（2026-09-22）

素材：`assets/man1.jpg`（860x574，人脸框仅 88x108）+ `assets/me.mp3`。
固定其余参数，各出 4 秒/100 帧，在第 50 帧同一位置比对。

### 11.1 先定噪声底

同一配置连跑两次，逐像素 `absdiff`：

```
base vs base2 : max=16  mean=0.31   ← 主要是 h264 编码差异
```

**低于这个量级的差异一律视为无效。** 这是判断"参数到底有没有用"的前提。

### 11.2 各参数的实际影响

| 对比 | max | 结论 |
|---|---|---|
| `parsing-mode` jaw→raw | 23 | ≈噪声，**无效旋钮** |
| `cheek-width` 90→140 | 48 | 仅融合边缘，**基本无效** |
| `upper-boundary-ratio` 0.5→0.62 | **143** | 热力图红点正落在嘴上，**真正有效** |
| `extra-margin` 10→4 / 0 | — | 嘴部变糊且更偏离原图，**调小是负优化** |

### 11.3 `upper-boundary-ratio` 的核心取舍

| 取值 | 口型运动幅度<br>(嘴部 ROI 逐帧均差) | 相对 base | 静止帧与原图差异<br>(嘴部 ROI mean) |
|---|---|---|---|
| 0.5（官方默认） | **4.2** | — | 11.7 |
| 0.55 | 4.0 | −5% | 11.6 |
| **0.58（当前默认）** | **4.0** | **−6%** | 11.1 |
| 0.62 | 3.2 | **−25%** | **9.0** |
| 0.62 + margin 4 | — | — | 11.2（变差） |
| 0.62 + margin 0 | — | — | 12.9（最差） |

**怎么读这张表**：

- `ratio` 越大 → 融合区上边界越往下压 → **原图的嘴保留得越多** →
  静止帧越像原图（9.0 最好），但**嘴动得越少（−25%）**。
- 换句话说，`0.62` 那个"更像原图"的分数，有相当一部分是**因为看到的本来就是原图的嘴**。
  对说话视频这是反效果——嘴不跟音频动，比接缝更假。
- 原图是**张嘴露齿笑**，而 `0.5` 会把这块表情整块换成生成的抿嘴，笑容直接丢失。
  这正是"看起来假"的主因之一。
- `0.58` 保住笑容的同时只损失 6% 运动幅度，因此作为默认值。

### 11.4 方案天花板（参数调不掉）

- **单图驱动**：上半脸完全静止，**不眨眼**。这是 MuseTalk 单图模式的固有限制。
- 人脸框仅 88x108，生成区下移后的下巴/颈部纹理偏软。
- 要突破这两条得换输入：用真人视频做 driving（MuseTalk 支持），
  或先对源图做人脸超分再喂。
